## O que construir

Entregar classificação Admin consultável e auditável, calcular o resultado mais restritivo e
derivar a allowlist/aprovação oficial do runtime. A decisão é vinculada ao hash do contrato e usa
concorrência otimista; metadata remota nunca concede read.

## Stack e geração de código

Backend Python existente. RNF/CLI não se aplica: a policy é uma extensão do módulo Python
`platform_ops`, com Azure Table e fake em memória seguindo os stores já adotados no repositório.

## Critérios de aceite

- [x] Apenas Admin grava `read|write` com motivo e `expectedRevision`; ETag conflitante retorna 409.
- [x] Chave contém tenant+source+tool+contractHash e toda decisão produz evento auditável.
- [x] Sem decisão é quarantined; `destructiveHint=true`/`readOnlyHint=false` elevam para write.
- [x] Policy/RBAC pode converter read/write em forbidden, nunca reduzir risco.
- [x] Runtime recebe somente tools conformes em `allowed_tools`; write usa aprovação nativa obrigatória.
- [x] Builder/Author consultam estado efetivo, mas não conseguem alterar classificação.

## Decisões / notas

- A decisão persiste em Azure Table por tenant, com RowKey SHA-256 de
	`sourceId+toolName+contractHash`; desenvolvimento e testes usam fake com o mesmo CAS.
- O evento de intenção é gravado antes do CAS. Falha de evidence impede persistência; conflito
	gera evento adicional e retorna 409.
- A projeção GET é autenticada para Builder/Author e mostra `effectiveEffect`; somente o PUT tem
	`require_role("Admin")`.
- `allowedTools` e `approvalMode` são derivados da mesma classificação. Metadata MCP só eleva
	risco, e write entra sempre em `always_require_approval`.
- O snapshot de rotas foi regenerado pelo comando oficial e incorporou também três rotas F03 que
	já existiam no app, mas ainda não estavam congeladas no fixture.
- O smoke precisou das variáveis sintéticas offline já usadas por `_capture_routes.py`; sem elas,
	o composition root exige `FOUNDRY_PROJECT_ENDPOINT` antes de abrir a porta.
