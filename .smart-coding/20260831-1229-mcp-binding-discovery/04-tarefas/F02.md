## O que construir

Evoluir `mcp-binding` para referenciar uma origem, uma allowlist pretendida e um snapshot revisado,
e entregar a decisão de conformidade consumível pelas fatias de publicação e UI. O documento não
carrega classificação, URL, conexão, auth ou estado executável.

## Stack e geração de código

Backend Python existente. RNF/CLI não se aplica porque a fatia altera schemas e serviços do módulo
Python `okf`; gerar artefato Node seria incompatível com o runtime e ADR-017. Reutilizar os padrões
estritos de `AuthoringInvalid` e as APIs públicas dos módulos.

## Critérios de aceite

- [ ] Schema aceita origem exclusiva Toolbox fixa, Toolbox default ou endpoint por id.
- [ ] `tools` é não vazia/única e `reviewedSnapshot` exige id+SHA-256; campos desconhecidos falham.
- [ ] `classification`, URL, connection/auth e chaves secret-like são recusadas recursivamente.
- [ ] Conformidade retorna `pass|block` com razões estáveis e valida source/snapshot/tools no mesmo tenant.
- [ ] `useDefault:true` resolve versão observada, mas a decisão exige materialização fixa pela F06.
- [ ] Referência cross-tenant responde como ausente, sem indicar existência.

## Decisões / notas

- A versão default é lida por `AIProjectClient.toolboxes.get` através da superfície pública de
	`foundry`; a conformidade sempre bloqueia `useDefault:true` até o binding ser materializado com
	versão fixa.
- Endpoint por id é estruturalmente válido, mas falha fechado como fonte ausente até a F03 entregar
	o registro tenant-scoped aprovado, sem acesso antecipado à rede.
- Antes de executar a F06, seu detalhe deve explicitar a materialização da default version já
	atribuída a ela pelo PRD, detalhamento e critério de aceite desta fatia.
