## O que construir

Entregar publicação GitHub da revisão aprovada por uma porta de domínio comum: Foundry Toolbox, servidor MCP oficial e OAuth identity passthrough criam branch, commit e pull request. Consentimento e aprovação nativa permanecem humanos; a aplicação não recebe nem persiste token.

## Stack e geração de código

- Skill: `sdk-verify` — verificar Learn, samples, MCP oficial e pacote instalado antes de fixar chamadas.
- Skill: `novo-modulo` — criar módulo de publicação somente se a responsabilidade ainda não tiver dono, com `public.py`/`internal/` e contratos completos.
- Skill: `rnf-validation` — aplicar validação/erros ao FastAPI Python, sem biblioteca RNF Node.
- Frontend: consentimento, progresso, PR e falhas explícitas no Assured UI.
- Justificativa RNF: integração e backend são Python; CLI RNF Node é incompatível.

## Critérios de aceite (verificáveis)

- [ ] Somente Approver da área inicia publicação de ChangeSet aprovado com hash idêntico.
- [ ] O adapter cria no máximo uma branch e um PR para a mesma chave de idempotência.
- [ ] Conteúdo enviado corresponde ao conjunto aprovado por canonicalização declarada.
- [ ] Token, header, URL de consentimento e resposta externa bruta não aparecem em banco, log, fixture ou OKF.
- [ ] Smoke autenticado prova branch, PR, consulta e replay idempotente em repositório de teste aprovado.

## Checklist NORDOR-122

- [ ] OAuth passthrough usa privilégio mínimo, consentimento e aprovação nativa.
- [ ] Repositório, ref, caminhos, tamanho e conteúdo são validados antes da chamada externa.
- [ ] Retry respeita `Retry-After`, limita três tentativas e só cobre falhas transitórias.
