## 1. Verdict

**Yes — parts of this repository emit OKF-conformant output today, and the conformance is
already gated in CI.** Four directories pass the specification's own §11 test
(`SPEC.md:738-744`) when checked with the vendored §11 validator: `openwiki/` (27 markdown
files, 0 errors), `knowledge/corpus/` (13 files, 0 errors),
`apps/backend/agents/assured/flows/` (5 files) and `apps/backend/agents/assured/copilots/`
(2 files). They satisfy rule 1 (parseable YAML frontmatter on every non-reserved `.md`),
rule 2 (non-empty `type`), and rule 3 (the seven `index.md` files carry no frontmatter
except the bundle root, per `SPEC.md:512-513`, and their bodies match the §8 section-plus-
bullet-list shape; there is no `log.md` in any bundle, which is legal — `SPEC.md:535` makes
it optional). The gate that holds this is `apps/backend/tests/knowledge/okf_conformance_test.py`,
wired into `.github/workflows/ci.yml:464`, and it runs a **third-party** validator
(`apps/backend/vendor/okf_validate.py`, 565 lines, copied 2026-08-30 per
`apps/backend/vendor/README.md:11-14`) rather than one written here. **The one artifact
that fails is the one users actually query:**
`knowledge/wiki-bundle/foundry-assured/v0.20260819/` — the bundle ingested into the Foundry
IQ knowledge base behind the `selfwiki` domain — fails §11 rules 1 and 2 on **19 of 19
pages**, because `adapt_openwiki.py:22-38` strips the frontmatter on the way in, and that
directory is not in the gate's bundle list. Separately, on the consume side, no repository
code rejects a document for a missing optional field, an unknown `type`, or a broken
cross-link *within an OKF bundle*: the retrieval path indexes body text only
(`retrieval.py:317` selects `snippet,blob_url`), so there is no §11 consume-side violation
in the grounding path.

## 5. Gaps — what is absent

Ordered by apparent size. Facts only; no recommendation attached.

**G1 — the ingested bundle carries no frontmatter at all.** 19/19 pages of
`knowledge/wiki-bundle/foundry-assured/v0.20260819/pages/` fail §11.1 and §11.2. Two
independent causes, both deliberate and both documented: the Foundry writer is told
"Saída: só o markdown da página (H2/H3), **sem frontmatter VitePress**"
(`wiki_builder.py:354`), and the OpenWiki adapter strips whatever frontmatter arrives
(`adapt_openwiki.py:22-24`). *(Size: the frontmatter is already computed upstream —
`openwiki/**` has it — so this is a transport decision, not missing data.)*

**G2 — no `generated`, `verified` or `sources` anywhere in a bundle.** All 20 concept
documents in `openwiki/` lack `generated` (`SPEC.md:377`, `by` required within it); so do
all 13 corpus runbooks, all 5 flows and both copilots. Zero documents in any bundle carry
`verified`, so under `SPEC.md:405` every concept in this repository is **unverified** to an
OKF consumer — including the pages a verifier pass actually rewrote. `adapt_openwiki.py:26-38`
states the cause in the code: `manifest.json` follows a vendored contract that must stay
"idêntico byte a byte" with its origin project, so the v0.2 trust fields have nowhere to
land, and are discarded rather than invented.

**G3 — generation is not distinguishable from verification in any artifact.** The verifier
in `wiki_builder.py:358-365` **rewrites the page in place**; the only trace that it ran is
the run log (`wiki_builder.py:389`, `" (verificada)"`) and the CLI flag `--no-verify`
(`:475`). Nothing in the page, the manifest or the bundle records that a verification
event happened, who performed it, or when — which is precisely the `generated` vs
`verified` distinction `SPEC.md:366-371` exists to carry.

**G4 — no `log.md` is produced by any path.** `SPEC.md:533-552` makes it optional, so this
is not a conformance failure. `adapt_openwiki.py:66` already lists it as a reserved file to
skip, so the consumer side is ready; there is no producer. The only `log.md` in the
repository is `skill-observations/log.md`, which sits outside every bundle.

**G5 — `okf_version` is declared as `"0.1"`.** `openwiki/index.md:2` reads
`okf_version: "0.1"`. The validator warns about it (`vendor/okf_validate.py:331-334`,
"§12 bundle declares `okf_version: \"0.1\"`; checked against v0.2"), but the gate only
fails on errors (`okf_conformance_test.py:90`), so the warning has never blocked a merge.
The gate's own comment at `okf_conformance_test.py:41-42` says the bundle "declara
`okf_version` desde sempre" — true, but not at the version the file's title claims.
*(Size: one line, plus a decision about whether the bundle should also gain the v0.2
fields the declaration would then imply.)*

**G6 — the gate's bundle list is hand-maintained.** `okf_conformance_test.py:40-50` names

### Attested Computation applicability (task 7)

Answered from `apps/backend/eval/` only, as the audit spec requires, in three sentences.
**The attester half maps cleanly:** `eval/assertions.py:1-13` and
`eval/wiki_fidelity_test.py:85-100` are deterministic, no-LLM code that reads an artifact
and returns a verdict against a floor declared once in `eval/assurance.yaml` — structurally
the `attester.resource` of `SPEC.md:604-606`, with the threshold playing the part of a
stored contract. **The executor and receipt halves do not exist:** nothing under `eval/`
declares run instructions or a `receipt` shape a run must return (`SPEC.md:599-603`); the
gates re-read the whole committed bundle at CI time (`wiki_fidelity_test.py:85`, over
`gather_source(REPO_ROOT)`) rather than inspecting evidence a single run emitted, and
`eval/run_eval.py:1-11` *invokes* the agent and scores it rather than verifying that
someone else ran a sanctioned computation. **So the analogy holds on the doc-level
`verified` axis and breaks on the per-run attestation axis** (`SPEC.md:721-732`): there is
no concept in any bundle carrying a sanctioned computation, no `runtime`/`parameters`
surface an agent may only fill values into (`SPEC.md:662-663`), and no receipt — these are
CI gates over artifacts, not per-call attestations.

## 7. Incidental defects

These are bugs regardless of any OKF decision.

**1. The ingested bundle is outside the conformance gate.**
`knowledge/wiki-bundle/**` is the artifact users actually query through `selfwiki`
(`ingest_docbundles.py:637`), and it is the only wiki artifact **not** in
`okf_conformance_test.py:40-50`. It fails §11 on every page. Whether it *should* be a
bundle is an open question (§8, Q1) — but its absence from the list is not visible from
the gate's output, which prints "✅ os 4 bundles são OKF v0.2 conformantes".

**2. `openwiki/index.md:2` declares `okf_version: "0.1"`** while the gate that checks it is
titled "OKF v0.2" and the frontend comment at `lib/okf.ts:17` cites `openwiki/index.md` as
evidence that "este repositório já é produtor OKF". The validator warns; the gate discards
warnings (`okf_conformance_test.py:88-90`).

**3. `docs/superpowers/specs/2026-08-17-user-managed-agents-and-knowledge-design.md:3` has
a frontmatter block that does not parse.** The unquoted `description` contains
`API oficial: 23 operações` — a `: ` inside an unquoted YAML scalar. `yaml.safe_load`
raises `mapping values are not allowed here` at line 2, column 316. Every naive
`startswith("---")` check counts this file as having frontmatter; the vendored validator
counts it as one of the 60 §11.1 errors in `docs/`. It has no runtime effect today only
because `docs/` is never ingested — `ingest.py:162-165` would `sys.exit` on it.

**4. `wiki-page-writer/SKILL.md:47-54` mandates VitePress frontmatter** (`title`,
`description` — no `type`), and `wiki_builder.py:354` explicitly overrides that instruction
in the same pipeline that loads the skill (`wiki_builder.py:198-200`). The skill's own
frontmatter template would also fail §11.2 for lacking `type`.

**5. `docs/superpowers/specs/2026-08-27-docbundle-vs-okf-medicao.md:12` attributes SPEC.md
to the wrong repository:** "OKF v0.2 SPEC.md, `GoogleCloudPlatform/knowledge-catalog`
(1006 linhas, lida por inteiro)". 1006 lines is exactly the line count of
`open-knowledge-format/SPEC.md@ad30107`, so the right file was read and the wrong repo was
cited. This is the only `knowledge-catalog` reference in the repository; `grep -rn
"knowledge-catalog"` finds no other, and no code or link resolves to that path.

**6. Documented count drift:** `CLAUDE.md` states the decisions live in "**ADRs 001–023**",
while `docs/adr/` holds 33 ADRs (001–033), including `ADR-032`, which is about OKF.

### Security note (audit spec §7.3)

§7.3 asks for a flag if any frontmatter field influences an access decision. **One does.**
`app/modules/knowledge/internal/frontmatter.py:60` (`declared_groups`) reads a `groups:`
key from a document's frontmatter, and `ingest.py:167-177` uses it as the document's
allowed-groups stamp, which becomes the Azure AI Search permission filter
(`acl_setup.py:125`). This is by design and documented as ADR-031 ("a fonte carrega o
próprio acesso"), matching how Graph connectors and Kendra attach ACLs to items.

Three facts that bound it, all verified:

- **It is not an OKF trust field.** `groups` is a producer-defined key; the spec's trust
  tiers (`SPEC.md:401-410`, explicitly "advisory signals, not access control") are **not
  read anywhere** in this repository. `grep -rn "verified" app/modules/knowledge/` finds no
  access use.
- **It is fail-closed in both directions.** Absent key ⇒ `None` ⇒ "does not declare"
  (`frontmatter.py:66-67`); present-but-wrong-type ⇒ `[]` ⇒ "no group may read"
  (`frontmatter.py:75`); a malformed YAML block **raises** rather than reading as absence
  (`frontmatter.py:50-56`); a key collision between two documents is a hard exit
  (`ingest.py:171-176`).
- **It is dormant on committed content.** `grep -rn "^groups:"` across every `.md` in the
  repository returns **nothing**. Today the live source of ACLs is the external
  `ACL_CLASSIFICATION` JSON (`acl_setup.py:71-77`), which is gitignored.

Recorded as a security finding per §7.3, not as an OKF opportunity. Nothing in this audit
proposes moving an access decision into frontmatter — it is already there, and the finding
is that it is there.

## 8. Open questions

Phrased as questions with the file or command needed to settle each. Several are the audit
spec's §7 decisions, restated as still open.

**Q1 — Is `knowledge/wiki-bundle/**` meant to be an OKF bundle, or an ingest transport
format?** `adapt_openwiki.py:26-38` argues it cannot carry OKF trust fields because
`docbundle.schema.json` is a vendored contract that must stay byte-identical to its origin
project, and proposes "um arquivo AO LADO do manifest". The answer decides whether defect 1
is a gap or a non-issue. *Needed:* the origin project's ownership of
`apps/backend/app/modules/knowledge/docbundle.schema.json` — who may change it, and whether
a sidecar has already been agreed.

**Q2 — (audit spec §7.1) Which capabilities depend on the format and which on the
pipeline?** This audit establishes the split factually: the OKF **format** is what
`openwiki/`, `knowledge/corpus/` and `agents/assured/{flows,copilots}/` already satisfy and
what the CI gate protects; the OpenWiki **pipeline** is one of three producers behind
`adapt_openwiki.py`, and the fidelity gate (`eval/wiki_fidelity_test.py`) is producer-
agnostic by construction. Adopting one does not require the other. The decision remains
yours.

**Q3 — (audit spec §7.2) Is a `log.md` worth its prompt surface?** New evidence: OpenWiki
does **not** generate one (drift D4), so "adopt OpenWiki" would not supply it. Anything
here would be built.

**Q4 — (audit spec §7.3) Access control stays out of frontmatter — but it is already
there.** See the security note above. The question this raises is not whether to move a
decision in, but whether the existing `groups` path should stay, given it is dormant on
committed content while `ACL_CLASSIFICATION` carries the live ACLs. *Needed:* whether any
deployed environment ships a corpus document with a `groups:` key — not answerable from
this repository.

**Q5 — Should the `openwiki/` bundle declare `okf_version: "0.2"`?** Changing the string is
one line, but `SPEC.md:776-780` frames the declaration as "the version they target", and
the bundle carries none of the v0.2 families (gap G2). *Needed:* your decision on whether
the declaration should follow the content or lead it.

**Q6 — Does the `openwiki` CLI at 0.4.0+ emit `generated` in this repo's shape?** OpenWiki's
own dogfooded wiki carries `generated: { by: "openwiki/0.4.0", at: … }`
(`openwiki/openwiki/concepts/okf-output.md:25` in the clone), while ours carries none —
consistent with our `openwiki/` having been produced by an older version
(`openwiki/.last-update.json` records `2026-08-19`, model `gpt-5.4`, but no CLI version).
*Needed:* a re-run of `openwiki --update` in a throwaway clone — which the audit spec §1
forbids doing here — or the CLI version recorded somewhere I did not find.

**Q7 — Was the OKF spec's canonical repo really moved?** Drift D7 could not be settled from
the two pinned clones. *Needed:* `git clone --depth 1 https://github.com/GoogleCloudPlatform/knowledge-catalog`
and a read of its `okf/README.md`.
